# 忘却曲線カレンダー 仕様書

> そのメモ、もちろん忘れます

## 1. コンセプト

その日書いたメモを、忘却曲線に沿って未来の日付に自動配置し、
「思い出し直すタスク」としてカレンダー上に積み上げていくメモ帳。

- メモを書く → 忘却曲線に沿った復習日が自動生成される
- カレンダーを開く → その日に思い出し直すべき過去のメモが積み上がっている
- 思い出せたか否かを記録する → 残りの復習日が自動で再スケジュールされる

## 2. 対象環境

- 静的サイト（ビルド不要）。GitHub Pages で公開。
- スマートフォン / タブレット / PC の全レスポンシブ対応。
- データはブラウザの `IndexedDB` にメモ 1 件ずつ保存（使えない環境では `localStorage`）。端末内で完結。サーバ送信なし。
- モダンブラウザ（ES Modules / CSS custom properties 対応）。

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| メモ (Note) | ユーザーが書いた本文。復習スケジュールの発生源。 |
| 追加メモ (Child Note) | 既存メモに紐付けて書くメモ。独立した忘却曲線を持つ。 |
| 復習 (Review) | ある日付に発生する「思い出し直すタスク」。 |
| ステップ (Step) | 復習が忘却曲線の何番目かを表す 0 始まりのインデックス。 |
| 定着 (Graduated) | 全ステップを終えた状態。カレンダーから外れる。 |
| 定着度 (Ease) | 記憶の定着しやすさ係数。再スケジュール時の倍率に使う。 |

## 4. データモデル (schema v5)

```jsonc
{
  "schemaVersion": 5,
  "notes": [
    {
      "id": "n_xxxxxxxx",
      "parentId": null,            // 追加メモなら親メモの id
      "title": "",
      "cue": "減価償却の3つの方法は？",  // 思い出すための手掛かり（任意）
      "body": "本文",
      "tags": ["tag1"],
      "anchorDate": "2026-09-17",  // 起点日（通常は作成日）
      "createdAt": "ISO8601",
      "updatedAt": "ISO8601",
      "status": "active",          // active | graduated | archived | inbox（復習なし）
      "color": null,

      // 起点：作成時に決めた曲線と分散。以後変わらない（変更は reschedule イベント）
      "origin": {
        "presetId": "standard",
        "intervals": [1, 3, 7, 14, 30, 60, 120, 240, 480, 960, 1920],
        "spread": 0.12,   // 分散の強さ（0 で分散なし）
        "seed": 4721      // 分散のシード（0-9999、ユーザーが変更可）
      },

      // 出来事：起きたことを順に積む（唯一の真実）
      "events": [
        { "id": "e_x", "type": "rate", "at": "ISO8601", "day": "2026-09-18",
          "reviewKey": "g0", "step": 0, "rating": "known" }
      ],

      // 以下は events から導出されるキャッシュ（保存はするが、読み込み時に再生成する）
      "schedule": { "presetId": "standard", "intervals": [...], "ease": 2.6, "adaptive": true },
      "reviews": [
        { "id": "g1", "step": 1, "due": "2026-09-20", "status": "pending",
          "rating": null, "completedAt": null, "extra": false }
      ]
    }
  ],
  "settings": { /* 5章 */ },

  // 日ごとの活動（9.3 節）。書いた日が後の編集で消えないように残す
  "activity": {
    "2026-09-17": { "notes": ["n_xxxxxxxx"], "chars": 320 }
  },

  // デイリーミッション（9.2 節）。バックアップにも含まれる
  "progress": {
    "points": 180,
    "streak": { "current": 3, "best": 7, "lastDay": "2026-09-18", "shields": 1 },
    "days": {
      "2026-09-18": {
        "ids": ["recall-some", "write-one", "peek-future"],  // その日のお題（初回に確定）
        "targets": { "recall-some": 3 },                      // 必要な数（初回に確定）
        "done": ["write-one"],
        "flags": { "peeked": true },   // 画面の操作で満たすもの
        "chars": 320,                  // その日に増えた本文の文字数
        "points": 15,
        "bonusAt": null,
        "celebrated": false
      }
    }
  },
  "meta": { "createdAt": "ISO8601", "updatedAt": "ISO8601", "appVersion": "0.6.1" }
}
```

### 4.1 出来事 (events)

| type | 内容 | 追加フィールド |
| --- | --- | --- |
| `rate` | 想起結果を記録した | `reviewKey`, `step`, `rating` |
| `skip` | その回を飛ばした | `reviewKey`, `step` |
| `postpone` | 予定日をずらした | `reviewKey`, `step`, `due` |
| `restart` | 今日を起点に組み直した | — |
| `reschedule` | 曲線・分散・シードを変えた | `presetId`, `intervals`, `spread`, `seed` |

`reviewKey` は再生中に生成される安定キー（`g0`, `g1`, …）。再生は決定的なので、
同じ出来事からは必ず同じ予定が得られる。

復習はメモに内包する。これによりメモ単位のエクスポート／削除でスケジュールが破綻しない。
カレンダー描画用の「日付 → 復習」インデックスは読み込み時にメモリ上で構築する。

## 5. 設定項目

| キー | 既定値 | 内容 |
| --- | --- | --- |
| `theme` | `system` | `system` / `light` / `dark` |
| `presetId` | `standard` | 既定の忘却曲線プリセット |
| `customIntervals` | `[1,3,7,14,30,60]` | `custom` プリセットの間隔（日） |
| `adaptive` | `true` | 想起結果に応じた再スケジュールを行う（既存メモにも適用） |
| `hideBodyUntilRecall` | `true` | 復習時は手掛かりだけを見せ、操作して本文を開く |
| `spreadId` | `normal` | 復習日の分散の強さ（none / small / normal / large） |
| `weekStart` | `0` | 週の開始曜日（0=日曜 / 1=月曜） |
| `carryOverOverdue` | `true` | 期限超過の復習を「今日」に繰り越して表示 |
| `overdueDailyLimit` | `10` | 1 日に取り戻す期限切れの上限（0 = すべて）。その日に取り戻した数を差し引くので補充されない |
| `showCreatedOnCalendar` | `true` | 作成されたメモもカレンダーに表示 |
| `defaultExportFormat` | `markdown` | エクスポートの既定形式 |
| `missionsEnabled` | `true` | デイリーミッションの表示と判定 |

## 6. 忘却曲線エンジン

### 6.1 プリセット

| ID | 名称 | 回数 | 最長 |
| --- | --- | --- | --- |
| `none` | あとで決める | 0 | 復習予定を作らない（status = `inbox`） |
| `standard` | 標準 | 11 | 約 5 年 |
| `intensive` | 集中 | 13 | 約 4 年 |
| `light` | ゆるめ | 9 | 約 8 年 |
| `lifelong` | 一生もの | 12 | 約 30 年 |
| `custom` | カスタム | 任意 | 最大 100 年 |

間隔は「日数」で持ち、遠い先ほど大きく開く（例: 標準は 1, 3, 7, 14, 30, 60, 120,
240, 480, 960, 1920 日）。年単位まで伸ばしても回数はさほど増えないため、
「いつかまた目に触れる」という感覚を保ったまま長く付き合える。

### 6.2 初期スケジュール生成

メモ作成時、`anchorDate + intervals[i]` 日の位置に step=i の復習を生成する。
つまり作成直後からカレンダーの未来日に復習タスクが並ぶ。

### 6.2.1 復習日の分散（シード）

同じ日に複数のメモを書くと、間隔が同じである以上、未来の復習日もすべて同じ日に重なる。
これを避けるため、メモごとに **シード**（0〜9999）を持たせ、各回の間隔にゆらぎを与える。

```
ずらす量 = round(間隔 × ratio × jitter(seed, step))    jitter ∈ [-1, 1]
```

- `ratio` は設定（none 0 / small 0.06 / normal 0.12 / large 0.22）
- ずらす量は**間隔に比例**するので、翌日（1 日）は四捨五入で 0 になり動かない。
  一方 1 年後（365 日）なら ±44 日、5 年後なら ±8 ヶ月ほど散る
- 並び順は必ず保つ（前の回より最低 1 日あと）
- 同じシードなら常に同じ結果（再生の決定性を壊さない）
- シードはユーザーが編集画面で変更でき、変更は `reschedule` イベントとして記録される
  （完了済みの履歴は保たれ、未来の予定だけが組み直される）

`origin.intervals` はプリセットそのままの値を保持し、分散を適用した実効間隔は
再生時に導出する。プリセットの表示は常にきれいな数字のままになる。

### 6.3 想起結果による再スケジュール（`adaptive` が有効な場合）

| 評価 | ease 変化 | 挙動 |
| --- | --- | --- |
| 覚えていた (`known`) | +0.10 | 次のステップへ進む |
| あいまい (`vague`) | -0.10 | 同ステップの追加復習を短い間隔で 1 回挿入してから次へ |
| 忘れた (`forgot`) | -0.25 | ステップ 0 から組み直す（完了日を新たな起点とする） |

- `adaptive` が無効な場合は想起結果を記録するだけで、作成時に決めた予定日は動かさない。
- `ease` は 1.3 〜 3.0 でクランプ。
- 倍率 `factor = ease / 2.5`。
- 未完了の復習 `j` の新しい期限は `完了日 + max(1, round((intervals[j] - intervals[i]) * factor))`。
- 全ステップ完了で `status = "graduated"`。「もう一周」で再開できる。

### 6.4 期限超過（思い出し待ち）

期限を過ぎた `pending` 復習は「思い出し待ち」として扱う。

- カレンダー上の日付自体は変更しない（履歴を壊さない）。
- `carryOverOverdue` が有効なら「今日」のキューへ繰り越す。
- 同じメモが何回分もたまっている場合は、いちばん古い 1 件だけをキューに出す
  （1 件記録すれば残りは自動で組み直されるため）。
- `overdueDailyLimit` 件までに絞り、残りは順番待ちとして保つ。
  「未達」「失敗」ではなく「思い出し待ち」と表示し、負債感を持たせない。

### 6.4.1 今日はここまで

`overdueDailyLimit` は「その日に取り戻した件数」を差し引いて数える。
こなしても次が補充されないため、「今日はこの件数だけで大丈夫」という約束が守られる。
追加でやりたいときは、本人が「もう少しやる」を押したときだけ上限を超えて出す。
今日カード・日別パネル・まとめて復習は、すべて同じ `todayQueue()` を見る。

### 6.5 取り消し

想起の記録は `events` の追加なので、取り消しは「最後の出来事を取り除いて再生し直す」
だけで済む。`ease` も未来の予定も記録前の状態に正確に戻る。
取り消せるのは常に最後の出来事のみ（履歴の途中を書き換えない）。

  中身をスクロールしている途中はスクロールを優先する。PC では中央のダイアログなので出さない
- トースト通知、確認ダイアログ

### 7.1 復習の流れ（v0.2 の中心）

「読んで自己評価」ではなく「思い出してから答え合わせ」にする。

```
手掛かり（cue またはタイトル）を見る
   ↓  頭の中で思い出す
［内容を見る］
   ↓  本文が開く
［覚えていた / あいまい / 忘れた］
   ↓
次の復習日が決まる
```

`hideBodyUntilRecall` を切ると、従来どおり最初から本文を表示する。

## 8. 出力・バックアップ

アプリバー右上のボタンから、いつでもバックアップを保存できる。
`meta.lastBackupAt` を持ち、最後の保存からの日数を表示する。
1 週間以上たっていて、そのあとに変更がある場合は日数を色付きで出して促す
（一度も保存していない場合は印だけ）。

| 対象 | 形式 |
| --- | --- |
| メモ単体 / 選択範囲 / 全件 | Markdown (.md), プレーンテキスト (.txt), CSV (.csv), JSON (.json) |
| 全データ | JSON バックアップ（設定・スケジュール・履歴を含む完全復元可能な形式） |

復元は「置き換え」と「マージ（id 重複はスキップ）」を選択できる。

## 9. 拡張性のための設計方針

1. **ストレージ抽象化** — `StorageAdapter` インタフェース（すべて非同期の `load` / `save` / `clear`）
   越しに読み書きする。IndexedDB やクラウド同期はアダプタ差し替えで対応できる。
   保存できない環境（プライベートモード等）は `persistent: false` を返し、UI が警告を出す。
2. **スキーマバージョン管理** — `schemaVersion` とマイグレーション関数チェーンを用意。
3. **出来事ベースのスケジューラ** — 予定は `origin + events` の再生結果。
   アルゴリズム追加（SM-2 / FSRS など）は `replay()` の分岐を差し替えるだけでよく、
   過去の記録を作り直す必要がない。取り消し・統計・将来の同期も出来事列から導ける。
4. **状態の一元管理** — `core/store.js` が単一の真実の源。UI は購読して再描画する。
5. **ビルドレス ES Modules** — 依存ゼロ。必要になった時点でバンドラを導入できる構成に留める。
6. **図は色だけに頼らない** — 想起結果の 3 色は、色覚特性を含む見分けやすさを数値検証した
   組み合わせを使い、凡例と数値ラベルを必ず添える。件数の濃淡は単一色相の連続スケール。

## 8.1 メモ編集画面（v0.5 / v0.7 で 1 枚の紙へ）

メモを選ぶと、アプリの表示領域すべてを使う編集画面に入る。

```
┌────────────────────────────┐
│ ←        ↶ ↷ ☰ 🔍 T ⓘ ⋮ │ ツールバー
├────────────────────────────┤
│ タイトル                     │ ┐
│ ◎ 思い出すための手掛かり      │ │ 1 枚の紙として
│ 本文 ……                     │ │ 一緒にスクロールする
│                            │ ┘
├────────────────────────────┤
│ 見出し リスト チェック 完了 …  │ ショートカットバー
├────────────────────────────┤
│ 保存済み            12字・3行 │ ステータスバー
└────────────────────────────┘
```

### なぜ 1 枚の紙にするか（v0.7）

手掛かりは、このアプリの復習の主役（復習では、まずこれだけが出る）。
それを「メモ情報」の中に隠すと、書くときに意識されない。
そこで **タイトル・手掛かり・本文を同じ紙の上に並べ**、開いた瞬間に目に入るようにした。

- 境界線は引かず、文字の大きさと色だけで役割を分ける（圧迫感を出さない）
- 上部に固定せず、本文と一緒にスクロールして消える
- 本文の textarea は中身の高さまで伸ばし（内部スクロールなし）、
  外側の `.ed__doc` がまとめてスクロールする
- 高さの測り直しは、増えているあいだは省いて「はみ出した分だけ足す」
- タイトル→手掛かり→本文は Enter / ↑↓ で行き来できる
- 空いたツールバーには、見出しへ移動・検索・表示設定・メモ情報を並べる

### 責務の分け方

| 層 | ファイル | 責務 |
| --- | --- | --- |
| 履歴 | `editor/history.js` | 元に戻す・やり直す（本文と選択範囲の組） |
| 中核 | `editor/textEditor.js` | 本文・選択範囲・行操作・コマンド登録 |
| 画面 | `ui/views/noteEditor.js` | ツールバー・保存・検索置換・メモ情報 |
| 保存 | `core/store.js` | 本文の保存と復習予定は別の操作として扱う |

編集機能はすべて **コマンド** として登録する。ツールバー・ショートカットバー・
キーボードのどれからでも `editor.run('bullet')` のように同じ処理を呼ぶ。
機能を足すときは `registerCommand()` で 1 つ増やすだけで、
エディタ本体や保存処理は書き換えない。

### ソフトキーボードへの追従

スマホでキーボードが出ると、画面の下側が隠れる。縮むのは「実際に見えている領域
(visualViewport)」で、`100dvh` などのレイアウト高さは変わらないため、
そのままでは下端のバーがキーボードの裏に回る。

- `ui/viewport.js` が visualViewport を監視し、CSS 変数へ流し込む
  （`--fcc-vv-height` / `--fcc-vv-top` / `--fcc-keyboard`、`data-keyboard="open"`）
- 編集画面は `position: fixed` + `height: var(--fcc-vv-height)` + `top: var(--fcc-vv-top)`
  で、見えている領域にぴったり収まる
- `interactive-widget=resizes-content`（viewport meta）で、対応ブラウザでは
  レイアウト自体も縮める
- キーボードが出ている間は下端の余白（ホームバー分）を詰める
- 領域が縮んだら、入力中の行が隠れないようカーソル位置へ寄せ直す

ショートカットバーは、狭い画面では文字を省いてアイコンだけにし、
横スクロールなしで全部が収まるようにする（幅 520px 以上で文字も表示）。

### 決めごと

- 本文の自動保存は入力の 700ms 後。`Ctrl/⌘+S` で即時保存
- 新規メモの id は最初の保存で一度だけ確保する（再試行で増やさない）
- 本文が空のまま閉じても、メモは作らない
- 日本語入力の変換中は履歴を刻まない（確定で 1 手）
- 一括置換は 1 手として戻せる
- 本文の前後の空白・改行は保存時に削らない
- 行の先頭の `# 〜 ######` は見出し。ツールバーの一覧（`Ctrl/⌘+K`）から移動できる
- ステータスバーの文字数を押すと、内訳（空白を除く・段落・英単語・読む目安）が出る
- 表示設定は、文字サイズ・行の間隔・折り返し・等幅・集中モード（バーを隠す）
- ステータスバーの数字は 150ms 間引いて出す（長いメモでも入力が重くならないように）
- 本文の編集では復習の予定・起点日を変更しない
- メモごとにカーソル位置とスクロール位置を覚える

## 9.1 書きかけの保護と保存の確実さ

| 課題 | 対応 |
| --- | --- |
| 入力中に閉じると消える | 入力のたびに下書きを `localStorage` へ保存（本体データとは別キー）。開くと復元し、「破棄」でのみ消える |
| 保存できたか分からない | `persist()` が成否を返し、エディタは `flush()` の成功を待ってから閉じる。失敗時は本文を保持して再試行・コピーを出す |
| 複数タブで上書き | 保存ごとに `meta.saveToken` を書き、保存前に他タブの書き込みを検出して取り込んでから書く。`storage` イベントでも取り込む |
| 統合で本文が消える | メモを丸ごと入れ替えず、**出来事は和集合・中身は `contentUpdatedAt` の新しい方**で統合する |
| 削除が復活する | `deleted`（墓標）を持ち、古いタブの保存で復活させない。復元は明示操作のときだけ |
| 保存できない環境 | アダプタが `persistent: false` を返し、画面上部に警告を出す |

統合の規則:

1. **出来事 (events)** — id の和集合。復習の記録は足し算なので失われない
2. **中身 (body / title / cue / tags)** — `contentUpdatedAt` が新しい方を採用。
   本文が食い違った場合、古い方は `conflicts` に退避し、編集画面で確認できる
3. **削除** — `deleted[id]` が相手のメモの更新時刻より新しければ、そのメモは復活させない

どちらのタブで書いた内容も、黙って失われないことを優先する。

## 9.2 デイリーミッション（v0.6）

毎日ここへ戻ってくる理由を、アプリ本来の使い方の中から作る。ロジックは
`core/missions.js`（純粋関数）、状態は `store.progress`、UI は `ui/missions.js`。

### 9.2.1 原則

1. **水増しさせない** — 要求はその日の予定の範囲内。`recall` 系の必要数は
   「今日向き合う予定だった件数」から作り、上限（5 件／やりきりは 12 件まで）を設ける。
2. **罰を作らない** — できない日があっても減点はない。連続は「おまもり」で
   1 日ぶん肩代わりでき、途切れても最長記録は残る。
3. **その日のうちは動かない** — お題と必要な数は、その日の最初の同期で `days[day]` に
   焼き付ける。復習を進めても目標が動かず、達成が遠のかない。
4. **同じ日なら同じお題** — 日付から決まる乱数（FNV-1a → mulberry32）で選ぶので、
   何度開いても、別のタブで開いても同じ。
5. **やめられる** — 設定 `missionsEnabled` でオフ。記録は残したまま表示だけが消える。

### 9.2.2 4 つの枠

| 枠 | 出るお題 | 判定に使う事実 |
| --- | --- | --- |
| recall（思い出す） | 今日の復習を N 件 / やりきる / 10 件まとめて / 「覚えていた」を 5 回 / 1ヶ月より前のメモに再会 | `rate` 出来事の当日件数と内訳、今日のキュー |
| write（書く） | メモを 1 つ・3 つ / 200 文字・500 文字 | `createdAt`・当日の増加文字数 |
| grow（育てる） | 前のメモに書き足す / 3 つのメモに触れる / 追加メモを 1〜2 つ / あとで決めるに曲線を組む | `contentUpdatedAt`・活動の記録・`parentId`・`restart` 出来事 |
| extra（おまけ） | 先の月をのぞく / 昔のメモを開く / バックアップ | 画面操作のフラグ・`lastBackupAt` |

その日にできるものが無い枠は飛ばす（メモが無い初日は 2 つになる）。
**数をこなすお題**（10 件まとめて・3 つ書く・500 文字）は、その日の予定や
これまでのメモ数が足りているときだけ出す。上限も設けて、予定を超える要求はしない。

### 9.2.3 ポイント・レベル・連続

- ポイントはお題ごと（10〜25 pt）＋全部そろえたボーナス 20 pt。
- レベル n の必要累計は `25n(n+1)`（Lv1=50 / Lv2=150 / Lv3=300…）。称号は 0/1/3/5/8/12/16/20 で変わる。
- 連続は「その日のお題を 1 つでも満たした日」を数える（v0.6.1〜）。意味のある行動が 1 つあれば
  その日は続いた日で、全部そろえるのはそこに乗るボーナス。7 日ごとに「おまもり」が 1 つ増え（最大 3）、
  空いた日数ぶんを自動で肩代わりする。使ったことは祝いの画面で本人に伝える。
- 別タブとの統合では、ポイントは多い方・連続は長い方・その日の達成は和集合を採る。

## 9.3 活動の記録（v0.6.1）

「この日に手を動かした」は、メモの `contentUpdatedAt` からは分からない。
後から書き足すと、前に書いた日が上書きされて消えてしまうため。
そこで `activity[日付] = { notes: [id], chars: n }` を別に持つ。

- `addNote` / `updateNote`（中身が変わったとき）に、その日の記録へ id と増えた文字数を足す
- `touchedDays()` は activity のキーを最優先に見る（過去の作成日・更新日・想起の記録も併せて数える）
- 文字数は「増えた分」だけ数える。消しても目減りしない
- 別タブとの統合では、触れたメモは和集合、文字数は多い方を採る

## 9.4 保存の確実さ（v0.6.1）

書いたものを失わないために、保存は次の決まりで動く。

1. **保存は 1 本の列に並べる** — 呼び出しは前の保存の後ろにつなぐ。
   保存中の呼び出しを「成功」と見なさない。
2. **保存中の入力を取りこぼさない** — 入力のたびに進む番号（revision）を保存の前後で見比べ、
   一致したときだけ「保存済み」にする。増えていれば、もう一度保存する。
3. **失敗したら画面を離れない** — 「一覧へ戻る」は保存の結果を見る。失敗したときは
   編集画面に留まり、再試行と本文のコピーを出す。
4. **空にする編集も保存する** — 「空の新規メモを作らない」判定は新規のときだけ。
   既存メモを空にしたら、空のまま保存する（削除は明示的な操作でだけ行う）。

## 9.5 今日のやる気くじ（v0.7.1）

その日のミッションをすべてそろえた人への、ごほうび。`core/omikuji.js`（純粋関数）。

- 運勢は 6 段階（大大吉 2% / 大吉 14% / 中吉 22% / 小吉 24% / 吉 24% / 末吉 14%）。**凶は作らない**
- 占いは 120 種類。読んで少し軽くなる言葉だけを入れる（責める言葉は入れない）
- 1 日 1 回。引いた結果は `progress.days[日付].omikuji` に残り、その日ぶん見返せる
- 直近 10 日ぶんに出た番号は避けて選ぶ（毎日ちがう言葉に出会えるように）
- くじは「ごほうび」であって、連続や達成の条件にはしない

## 9.5.1 書けるタブは 1 つだけ（v0.8）

データは 1 つのキーに丸ごと入っている。2 つのタブが同時に書くと、
あとから書いた方が相手の変更を丸ごと上書きしたり、取り消した記録が
相手のタブ経由で戻ってきたりする。統合で解こうとすると、削除・取り消し・
全消去の打ち消しまで表現する必要があり、壊れ方が見えにくくなる。

そこで **書けるのは 1 つのタブだけ** と決めた（`core/tabLock.js` / `ui/tabOwnership.js`）。

- 持ち主は `fcc.owner.v1` に印を置き、4 秒ごとに更新する（生存確認）
- あとから開いたタブは「見るだけ」。`store.readOnly = true` で保存を止め、
  画面には案内と［このタブで編集する］を出す（FAB と操作ボタンも触れなくする）
- 譲り受けるときは `fcc.owner.request.v1` に合図を置く。持ち主は
  **書きかけを保存してから**印を外す。返事が無ければ 1.2 秒後に引き継ぐ
- 印が 12 秒以上古ければ、そのタブは閉じられたものとして引き継ぐ
- 譲り受けた側は **統合せず `reload()`** する（「いま保存されているもの」が正しい）

この結果、同時保存による消失・取り消しの復活・全消去後の復活・
削除の取り消しやアーカイブの伝わらなさは、まとめて起きなくなる。
`reconcile()` は将来の同期アダプタ用に残すが、通常の動作では使わない。

## 9.5.2 保存のタイミング（v0.8）

| 操作 | 保存 |
| --- | --- |
| 本文の入力 | 400ms まとめて 1 回（書きかけの控えは 350ms ごと） |
| 想起の記録・スキップ・延期・組み直し | すぐ書き始める |
| 作成・削除・復元・アーカイブ・取り込み・全消去 | すぐ書き始める |
| くじ・ミッション・設定 | すぐ書き始める |
| タブを閉じる／画面から離れる | `flushSync()` で待たずにその場で書く |

バックアップの復元は、保存の結果を待ってから「できました」と伝える。

## 9.6 たくさんのメモに耐えるための設計（v0.7.1）

メモが数千件に増えても、書く・開く・探すが重くならないようにする。

| 仕組み | ねらい |
| --- | --- |
| メモ 1 件 = 1 レコード（IndexedDB・v0.9） | 1 文字の変更で全メモを書き直さない |
| 保存の予約（400ms でまとめて 1 回） | 1 文字ごとに全部を書き出さない |
| 保存の印を別キーに置く | 別タブの確認で、毎回すべてを読み解かない |
| 予定が変わらない編集は索引を作り直さない | 本文だけの編集を軽くする |
| その日の事実（missionContext）を版ごとに覚える | 同じ内容を何度も数え直さない |
| 親 id → 子メモの数を 1 回だけ数える | 一覧のカードごとの走査（O(n²)）をなくす |
| 一覧は 40 件ずつ描く（スクロールで追加） | 開いた瞬間を軽くする |
| 描画は 1 フレームに 1 回へまとめる | まとめて記録したときに画面作りを重ねない |
| 検索は 140ms 待ってから絞る | 打つたびに全件を走査しない |

実測（2000 件・PC の Chromium）: 起動 789ms / カレンダー 116ms / 一覧 84ms /
記録 100ms / 検索 7ms / 本文 1 文字の反映 38ms（書き込みは 400ms にまとめて 1 回・76ms）。

## 9.7 メモ単位の保存（v0.9）

`localStorage` は「文字列 1 本」なので、1 文字直すだけでも全メモを書き直すことになる。
メモが増えるほど 1 回の保存が重くなり、上限（数 MB）にも当たる。
そこで **メモ 1 件を 1 レコード**として持てる `IndexedDB` を既定の保存先にした
（`core/storage.js` の `IndexedDbAdapter`）。

### 9.7.1 保存先の構造

| ストア | 中身 |
| --- | --- |
| `notes`（keyPath: `id`） | メモ 1 件 = 1 レコード |
| `meta` | `rest`（設定・進み具合・活動記録・墓標・meta）と `token`（最後に保存したタブの印） |

読み込みは `notes` の全件と `rest` を合わせて、これまでと同じ形のデータに戻す。
移行（migrations.js）も正規化も、これまでと同じ経路を通る。

### 9.7.2 何を書くかの決め方

`store.js` は「前回の保存以降に変わったもの」を持ち、書く直前に plan を作る。

```
plan = { full, notes: 変わったメモだけ, removed: 消えたメモの id, rest }
```

- メモの版（`id -> updatedAt`）を保存できた時点で覚え、次の保存で見比べる
- 出来事（`note:update` など）に `noteId` があれば、そのメモも書く対象にする
- 設定・ミッション・くじ・バックアップだけの出来事は `rest` のみ書く
- **どちらとも言えない出来事は全部書き直す**（書き忘れるより多めに書く）
- 全メモの予定を組み直したとき（`refreshAll`）・取り込み・読み直し・
  保存先の差し替えも全部書き直す
- 書けなかったぶんは変更の記録へ戻し、次の保存で必ず書き直す

plan は「取り込みが済んだ書く直前」に作る。待っている間に増えた変更は
次の plan で拾えるので、保存中の入力も取りこぼさない。

### 9.7.3 閉じる直前（IndexedDB は同期で書けない）

`flushSync()` は待ってもらえない場面で使うが、IndexedDB に同期の API は無い。
そこで **控え（journal）を `localStorage` に同期で置き**、本体へは非同期で書きに行く。

- 次回の読み込みで、控えの印と保存先の印が違えば控えを重ねて取り戻す
- 印が同じ（本体への書き込みが間に合っていた）なら、控えを捨てる
- 保存が成功したら控えは消える。控えは常に 1 回ぶんなので小さい
- 控えを置けても本体に入ったかは分からないので、**変更の記録は消さない**。
  閉じきらずに使い続けたときは、次の保存でもう一度書く

### 9.7.4 これまでのデータからの移行

1. `IndexedDB` が開けて、すでに中身があるならそれを使う
2. 開けたけれど空なら、`localStorage` の本体（無ければ移行前の控え）から移す。
   移したあと、本体は `fcc.data.v1.pre-idb` へ寄せて「移行前の控え」として残す
3. 開けなければ `localStorage` を使う。このとき控えが残っていれば本体へ戻す

控えを残すのは、`IndexedDB` が使えない環境（プライベートモードなど）へ
持ち込んだときに、何も無い状態で始まらないようにするため。
移行元として控えを見るのは保存先がまっさらなときだけで、
「全消去」では控えも消す（消したものが戻ってこないように）。

### 9.7.5 書いてよいかの確認は 1 回だけ

保存のたびに「別タブが先に書いていないか」を確かめると、読み出しが増えて遅くなる。
書けるタブは 1 つだけ（9.5.1）なので、**読み込み直後の 1 回**と
**編集できるタブに戻ったとき**だけ確かめる。

### 9.7.6 実測（PC の Chromium）

| | 2000 件（3.6MB） | 5000 件（9.1MB） |
| --- | --- | --- |
| 起動（読み込み〜描画） | 538ms | 895ms |
| 1 文字の保存で書く量 | 2.7KB | 2.7KB |
| 1 文字の保存で画面が止まる時間 | 0ms | 0ms |
| 1 文字の保存が終わるまで | 1ms | 1ms |
| （比較）localStorage で全件書き直し | 45ms 画面が止まる | **保存できない**（容量超過） |
| 本文 1 文字の反映 | 29ms | 68ms |
| カレンダー / 一覧 / 記録の描画 | 83 / 74 / 94ms | 181 / 65 / 165ms |

5000 件（約 9MB）は `localStorage` では保存そのものができない。
メモ単位の保存にしたことで、貯めた量が保存の重さに影響しなくなった。
